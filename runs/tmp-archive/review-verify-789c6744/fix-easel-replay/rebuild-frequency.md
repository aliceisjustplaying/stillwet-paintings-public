# Post-restore checks avoid most injected-failure rebuilds

On sampled round19 heaps, the frozen baseline's touched-table predicate would request a rebuild for **478/478 injected failures (100%)**. Comparing table contents and native `next` order **after** restore would request **118/478 (24.7%)**, avoiding **360/478 (75.3%)**. All 118 remaining mismatches were iteration order, not contents. These are conditional rates for synthetic failures, not estimates of how often real painting commands fail. Evidence: [raw measurements](rebuild-measurements.csv), generated by [aggregation script]([local path redacted]

Across 7,462 table observations, 478 tables were touched before restoration, zero had mismatched contents afterward and 118 had mismatched native order afterward. Repeated observations of the same tables are included; these are not 7,462 distinct tables. Evidence: CSV and aggregation script above.

## Method and scope

- Replayed the first eight chunks of each of the 10 matching `r19/run/*/p1_check/paintings/lua/painting.lua` logs, sequentially, in a 64-pixel-wide Session. Sampled after chunks 1, 4 and 8: 30 heap checkpoints with no skipped replay chunks. Logs: CTEST, GEMB, GEMF, LUNAB, LUNAF, MUSEF, NEWF, SELFH, SONB and SONF. Evidence: [run log]([local path redacted] [scratch harness]([local path redacted] Canvas `size` is physical millimeters, not replay resolution: [copied API]([local path redacted]
- Used a copied checkout and frozen heap implementation, not the concurrently edited shared source. Baseline SHA-256: `3a6916408c6f0d06d6e26cc49229ab30d3fab65399ca1099c396864b551e7f3e`. Evidence: [frozen heap]([local path redacted]
- Selected up to eight existing non-global reachable tables per checkpoint, each with 1–184 entries. Removed one existing key and inserted one or 16 synthetic string keys, then raised an explicit error inside `pcall`. Maximum targeted table size was 199 entries. Global injections inserted one new key then errored. Evidence: [diagnostic]([local path redacted]
- Recorded pre-restore content/order mismatch, baseline restore's touched count and independent post-restore content/order mismatch. Contents compare raw key/value identity, entry count and actual metatable identity. Order compares native `next` key sequences against the snapshot, without using painter `pairs`. Evidence: diagnostic lines 1–13 and 34–37; frozen heap lines 14–62 and 91–118.
- Bounded work: one Session at a time, eight replay chunks, three checkpoints, at most eight target tables, 16 inserted keys and a 90-second per-Session instruction-hook cap. Observed snapshots contained 8–150 tables; the diagnostic completed in 26.79 seconds. No full-resolution live replays were run. Evidence: scratch harness lines 1001–1024, CSV `tables` column and run log test result.

## Limitations

These trials mutate real logged heaps but do not replay naturally failing painting commands. The 100% before-restore rate is expected because every injection deliberately changes a table. The sample is limited to early chunks and low resolution. Selection follows native traversal of the snapshot and includes library/prelude tables as well as any reachable painting tables; the CSV does not identify individual target tables. Global tables are excluded from the table-selection size cap and tested separately with one added key. Evidence: harness lines 1016–1020 and diagnostic lines 18–29.

Trials reuse restored heaps. Each trial takes a fresh snapshot, but a preceding trial can leave a different table layout; later checkpoints also inherit those layouts. Thus these rates describe sequential rollback experiments, not independent failures from a freshly reopened pristine log. The many shared library tables also make observations correlated across logs. Evidence: diagnostic lines 23–40 and harness lines 1016–1024.

The checker measures tables, not upvalue identity or engine canvas/brush state. This diagnostic is a scratch-only measurement, not a production regression test or a measurement of the server agent's eventual fix. The instruction cap is not an allocator memory cap: the bounded input prefix and injection sizes constrain this experiment, not arbitrary hostile Lua. Evidence: diagnostic lines 1–13, harness lines 1004–1007 and frozen heap lines 110–114.

## Recommended approach

**Decide whether to rebuild from the restored heap, not from whether the failed command touched a table.** Restore contents and upvalues first, then compare every snapshotted table's actual metatable, raw contents and native `next` sequence against its saved record. Rebuild if any table still differs. Keep the saved native sequence: content-only equality would incorrectly skip the 118 order mismatches here. The baseline already stores that sequence and has an `untouched` comparator, but increments `changed` before restoration. Evidence: frozen heap lines 35–45, 67–76 and 91–107; measurement table above.

Residual order mismatches are common in these synthetic table-edit cases (118/448, 26.3%), especially 16-key growth (43.8%). Retain lazy replay for those cases rather than assuming clear/reinsert preserves layout. For future optimization, investigate native Lua table-layout rollback or restricting observable traversal to a deterministic API, but treat either as a separate design project requiring compatibility proof. The measured low-risk change is simply moving the rebuild decision after restoration; these data do not establish the correctness of those broader alternatives.
